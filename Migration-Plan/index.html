    CardDemo Migration Plan: Mainframe to Java Microservices

    Comprehensive migration plan for modernizing CardDemo from mainframe (COBOL/CICS/VSAM) to Java microservices with PostgreSQL database.

    Executive Summary

    Migration Overview

    Objective: Modernize the CardDemo credit card management application from mainframe technologies to cloud-native Java microservices architecture.

    Current State: Mainframe application with 29 COBOL programs, 10 VSAM files, 14 CICS transactions, 33 batch jobs

    Target State: Cloud-native microservices application with Java Spring Boot, PostgreSQL database, REST APIs, and modern UI

    Migration Approach: Strangler Fig Pattern - Incremental migration with coexistence of old and new systems

    Estimated Duration: 12-18 months (depending on team size and resources)

    Key Benefits: - Cloud scalability and elasticity - Modern development practices (CI/CD, DevOps) - Improved maintainability and agility - Cost reduction (mainframe licensing) - Enhanced user experience - API-first architecture for integration

    Current State Analysis

    Application Inventory

    Online Programs (29 COBOL Programs)

    User Functions: - COSGN00C - Sign-on and authentication - COMEN01C - Main menu navigation - COACTVWC, COACTUPC - Account view and update - COCRDLIC, COCRDSLC, COCRDUPC - Card management - COTRN00C, COTRN01C, COTRN02C - Transaction management - COBIL00C - Bill payment processing - CORPT00C - Report generation

    Admin Functions: - COADM01C - Admin menu - COUSR00C, COUSR01C, COUSR02C, COUSR03C - User management (CRUD)

    Optional Modules: - COPAUA0C, COPAUS0C, COPAUS1C - Authorization processing (IMS-DB2-MQ) - COTRTLIC, COTRTUPC - Transaction type management (DB2) - CODATE01, COACCT01 - Account extraction (VSAM-MQ)

    Batch Programs (33 JCL Jobs)

    Daily Processing: - CBTRN02C - Transaction posting - CBTRN03C - Transaction reports - Transaction backup and indexing

    Monthly Processing: - CBACT04C - Interest calculation - CBSTM03A - Statement generation

    Data Management: - File initialization and loading - Data extraction and transformation - Backup and recovery

    Data Stores (10 VSAM Files)

    • ACCTDAT - Account master (300 bytes/record)
    • CARDDAT - Card master (150 bytes/record)
    • CUSTDAT - Customer master (500 bytes/record)
    • CARDXREF - Cross-reference (50 bytes/record)
    • TRANSACT - Transaction history (350 bytes/record)
    • USRSEC - User security (80 bytes/record)
    • TRANTYPE, TRANCATG, DISCGRP, TCATBALF - Reference data

    Optional Data Stores

    • DB2 - Transaction types, fraud tracking
    • IMS DB - Authorization details (hierarchical)
    • MQ - Message queuing for async processing

    Architecture Characteristics

    Presentation Layer: - 3270 terminal screens (BMS maps) - Character-based UI (24x80) - Function key navigation

    Business Logic: - COBOL programs with embedded business rules - Pseudo-conversational CICS transactions - Copybook-based data structures

    Data Access: - VSAM indexed files (KSDS) - Alternate indexes for secondary keys - Batch/online file sharing with locking

    Integration: - MQ for asynchronous messaging - DB2 for relational data - IMS DB for hierarchical data

    Technical Debt Assessment

    Challenges: 1. Monolithic Structure: Tight coupling between presentation, business logic, and data access 2. Technology Lock-in: Mainframe-specific technologies (COBOL, CICS, VSAM) 3. Limited Scalability: Vertical scaling only, expensive hardware 4. Maintenance Burden: Aging technology, limited developer pool 5. Integration Complexity: Difficult to integrate with modern systems 6. User Experience: Outdated terminal-based interface 7. Testing Challenges: Limited automated testing capabilities 8. Deployment Rigidity: Infrequent releases, complex deployment process

    Strengths to Preserve: 1. Business Logic: Well-tested, proven business rules 2. Data Integrity: ACID transactions, data consistency 3. Performance: Optimized for high-volume transaction processing 4. Reliability: Proven stability and uptime 5. Security: Robust authentication and authorization

    Target Architecture

    Architecture Principles

    1. Microservices: Decompose monolith into independently deployable services
    2. API-First: RESTful APIs for all service interactions
    3. Cloud-Native: Designed for cloud deployment (AWS, Azure, GCP)
    4. Event-Driven: Asynchronous communication where appropriate
    5. Stateless: Services maintain no session state
    6. Database per Service: Each microservice owns its data
    7. Containerized: Docker containers for consistent deployment
    8. DevOps: CI/CD pipelines, automated testing, monitoring

    Technology Architecture

    Frontend: - React or Angular for web application - React Native or native iOS/Android for mobile - Material-UI or Bootstrap for UI components - Redux or NgRx for state management

    API Gateway: - Spring Cloud Gateway or Kong - OAuth 2.0 / JWT for authentication - Rate limiting and throttling - Request routing and load balancing

    Microservices: - Java 17+ with Spring Boot 3.x - Spring Cloud for microservices patterns - Spring Data JPA for data access - Spring Security for authentication/authorization - RESTful APIs with OpenAPI/Swagger documentation

    Data Layer: - PostgreSQL 15+ for relational data - Redis for caching - Flyway or Liquibase for schema migration - Connection pooling (HikariCP)

    Messaging: - Apache Kafka for event streaming - RabbitMQ or AWS SQS for message queuing - Spring Cloud Stream for messaging abstraction

    Infrastructure: - Docker for containerization - Kubernetes for orchestration - Service mesh (Istio or Linkerd) for service communication - Prometheus + Grafana for monitoring - ELK Stack (Elasticsearch, Logstash, Kibana) for logging - Jaeger or Zipkin for distributed tracing

    CI/CD: - Jenkins, GitLab CI, or GitHub Actions - SonarQube for code quality - JUnit, Mockito for unit testing - Testcontainers for integration testing - Selenium or Cypress for E2E testing

    Microservices Decomposition

    Service Boundaries

    1. Customer Service

    Responsibility: Manage customer information and profiles

    Functionality: - Customer CRUD operations - Customer search and lookup - Customer profile management - Address and contact management

    Data Owned: - Customer master data (from CUSTDAT)

    APIs: - POST /api/customers - Create customer - GET /api/customers/{id} - Get customer details - PUT /api/customers/{id} - Update customer - DELETE /api/customers/{id} - Delete customer - GET /api/customers/search - Search customers

    Source Programs: - Customer data access from CVCUS01Y copybook

    2. Account Service

    Responsibility: Manage credit card accounts

    Functionality: - Account CRUD operations - Account balance management - Credit limit management - Account status management - Account-customer relationship

    Data Owned: - Account master data (from ACCTDAT) - Account-customer relationships (from CARDXREF)

    APIs: - POST /api/accounts - Create account - GET /api/accounts/{id} - Get account details - PUT /api/accounts/{id} - Update account - GET /api/accounts/{id}/balance - Get balance - PUT /api/accounts/{id}/credit-limit - Update credit limit - GET /api/customers/{customerId}/accounts - Get customer accounts

    Source Programs: - COACTVWC - Account view logic - COACTUPC - Account update logic

    3. Card Service

    Responsibility: Manage credit cards

    Functionality: - Card CRUD operations - Card issuance and activation - Card status management (active, blocked, expired) - Card-account relationship - Card validation (Luhn algorithm)

    Data Owned: - Card master data (from CARDDAT) - Card cross-reference (from CARDXREF)

    APIs: - POST /api/cards - Issue new card - GET /api/cards/{cardNumber} - Get card details - PUT /api/cards/{cardNumber} - Update card - PUT /api/cards/{cardNumber}/status - Update card status - GET /api/accounts/{accountId}/cards - Get account cards - POST /api/cards/{cardNumber}/validate - Validate card

    Source Programs: - COCRDLIC - Card list logic - COCRDSLC - Card view logic - COCRDUPC - Card update logic

    4. Transaction Service

    Responsibility: Process and manage transactions

    Functionality: - Transaction creation and posting - Transaction history and search - Transaction categorization - Transaction validation - Real-time balance updates

    Data Owned: - Transaction history (from TRANSACT) - Transaction types (from TRANTYPE) - Transaction categories (from TRANCATG)

    APIs: - POST /api/transactions - Create transaction - GET /api/transactions/{id} - Get transaction details - GET /api/cards/{cardNumber}/transactions - Get card transactions - GET /api/accounts/{accountId}/transactions - Get account transactions - POST /api/transactions/search - Search transactions - GET /api/transactions/types - Get transaction types

    Source Programs: - COTRN00C - Transaction list logic - COTRN01C - Transaction view logic - COTRN02C - Transaction add logic - CBTRN02C - Transaction posting logic

    Events Published: - TransactionCreated - TransactionPosted - TransactionFailed

    5. Payment Service

    Responsibility: Process bill payments

    Functionality: - Payment processing - Payment validation - Balance adjustment - Payment history

    Data Owned: - Payment transactions (subset of TRANSACT)

    APIs: - POST /api/payments - Process payment - GET /api/payments/{id} - Get payment details - GET /api/accounts/{accountId}/payments - Get account payments - POST /api/payments/validate - Validate payment

    Source Programs: - COBIL00C - Bill payment logic

    Events Published: - PaymentProcessed - PaymentFailed

    6. Report Service

    Responsibility: Generate reports and statements

    Functionality: - Transaction reports - Account statements - Summary reports - Report scheduling - Report export (PDF, CSV)

    Data Owned: - Report definitions - Scheduled reports

    APIs: - POST /api/reports/transactions - Generate transaction report - POST /api/reports/statements/{accountId} - Generate statement - GET /api/reports/{id} - Get report - GET /api/reports/{id}/download - Download report

    Source Programs: - CORPT00C - Report generation logic - CBSTM03A - Statement generation logic

    7. User Service

    Responsibility: Manage application users and authentication

    Functionality: - User registration and management - User authentication - Password management - User roles and permissions - Session management

    Data Owned: - User credentials (from USRSEC) - User profiles - User sessions

    APIs: - POST /api/users/register - Register user - POST /api/users/login - User login - POST /api/users/logout - User logout - GET /api/users/{id} - Get user details - PUT /api/users/{id} - Update user - PUT /api/users/{id}/password - Change password - DELETE /api/users/{id} - Delete user

    Source Programs: - COSGN00C - Sign-on logic - COUSR00C, COUSR01C, COUSR02C, COUSR03C - User management logic

    8. Authorization Service (Optional Module)

    Responsibility: Real-time transaction authorization

    Functionality: - Authorization request processing - Fraud detection - Authorization history - Authorization rules engine

    Data Owned: - Authorization history - Fraud tracking data

    APIs: - POST /api/authorizations - Process authorization - GET /api/authorizations/{id} - Get authorization details - GET /api/cards/{cardNumber}/authorizations - Get card authorizations - PUT /api/authorizations/{id}/fraud - Mark as fraud

    Source Programs: - COPAUA0C - Authorization processing logic - COPAUS0C, COPAUS1C - Authorization inquiry logic

    Events Consumed: - AuthorizationRequest (from MQ)

    Events Published: - AuthorizationApproved - AuthorizationDeclined - FraudDetected

    Service Communication Patterns

    Synchronous (REST): - User Service → Customer Service (get customer details) - Account Service → Customer Service (validate customer) - Card Service → Account Service (validate account) - Transaction Service → Card Service (validate card) - Transaction Service → Account Service (update balance)

    Asynchronous (Events): - Transaction Service → Payment Service (transaction posted) - Transaction Service → Report Service (transaction created) - Authorization Service → Transaction Service (authorization approved) - Payment Service → Account Service (payment processed)

    Data Consistency: - Saga pattern for distributed transactions - Event sourcing for audit trail - Eventual consistency where appropriate - Compensating transactions for rollback

    Data Migration Strategy

    Database Schema Design

    PostgreSQL Schema Structure

    Database per Service Pattern: - customer_db - Customer Service database - account_db - Account Service database - card_db - Card Service database - transaction_db - Transaction Service database - user_db - User Service database - payment_db - Payment Service database - report_db - Report Service database

    Schema Mapping: VSAM to PostgreSQL

    Customer Schema (customer_db)

    Source: CUSTDAT VSAM file (CVCUS01Y copybook)

    CREATE TABLE customers (
    customer_id BIGINT PRIMARY KEY,
    first_name VARCHAR(25) NOT NULL,
    middle_name VARCHAR(25),
    last_name VARCHAR(25) NOT NULL,
    address_line1 VARCHAR(50),
    address_line2 VARCHAR(50),
    address_line3 VARCHAR(50),
    state_code VARCHAR(2),
    country_code VARCHAR(3),
    zip_code VARCHAR(10),
    phone_number1 VARCHAR(15),
    phone_number2 VARCHAR(15),
    ssn VARCHAR(9),
    govt_issued_id VARCHAR(20),
    date_of_birth DATE,
    eft_account_id VARCHAR(10),
    primary_card_holder_ind CHAR(1),
    fico_credit_score SMALLINT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    version INTEGER DEFAULT 0
);

CREATE INDEX idx_customers_ssn ON customers(ssn);
CREATE INDEX idx_customers_name ON customers(last_name, first_name);

    Migration Notes: - CUST-ID (PIC 9(09)) → customer_id (BIGINT) - Date format conversion: YYYY-MM-DD string → DATE type - Add audit columns: created_at, updated_at, version - Add indexes for common queries

    Account Schema (account_db)

    Source: ACCTDAT VSAM file (CVACT01Y copybook)

    CREATE TABLE accounts (
    account_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    active_status CHAR(1) NOT NULL DEFAULT 'Y',
    current_balance DECIMAL(12,2) NOT NULL DEFAULT 0.00,
    credit_limit DECIMAL(12,2) NOT NULL,
    cash_credit_limit DECIMAL(12,2) NOT NULL,
    open_date DATE NOT NULL,
    expiration_date DATE NOT NULL,
    reissue_date DATE,
    current_cycle_credit DECIMAL(12,2) DEFAULT 0.00,
    current_cycle_debit DECIMAL(12,2) DEFAULT 0.00,
    address_zip VARCHAR(10),
    group_id VARCHAR(10),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    version INTEGER DEFAULT 0,
    CONSTRAINT chk_balance CHECK (current_balance >= -credit_limit),
    CONSTRAINT chk_credit_limit CHECK (credit_limit >= 0),
    CONSTRAINT chk_cash_limit CHECK (cash_credit_limit <= credit_limit)
);

CREATE INDEX idx_accounts_customer ON accounts(customer_id);
CREATE INDEX idx_accounts_status ON accounts(active_status);

-- Account-Customer relationship
CREATE TABLE account_customers (
    account_id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    relationship_type VARCHAR(20) NOT NULL, -- PRIMARY, JOINT, AUTHORIZED
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (account_id, customer_id)
);

    Migration Notes: - ACCT-ID (PIC 9(11)) → account_id (BIGINT) - COMP-3 amounts → DECIMAL(12,2) - Add foreign key to customer (from CARDXREF) - Add check constraints for business rules - Separate table for account-customer relationships

    Card Schema (card_db)

    Source: CARDDAT VSAM file (CVACT02Y copybook)

    CREATE TABLE cards (
    card_number VARCHAR(16) PRIMARY KEY,
    account_id BIGINT NOT NULL,
    cvv_code VARCHAR(3) NOT NULL,
    embossed_name VARCHAR(50) NOT NULL,
    expiration_date DATE NOT NULL,
    active_status CHAR(1) NOT NULL DEFAULT 'Y',
    card_type VARCHAR(20) DEFAULT 'CREDIT', -- CREDIT, DEBIT
    issue_date DATE DEFAULT CURRENT_DATE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    version INTEGER DEFAULT 0,
    CONSTRAINT chk_card_status CHECK (active_status IN ('Y', 'N', 'B', 'E'))
);

CREATE INDEX idx_cards_account ON cards(account_id);
CREATE INDEX idx_cards_status ON cards(active_status);
CREATE INDEX idx_cards_expiration ON cards(expiration_date);

-- Card-Account-Customer cross reference
CREATE TABLE card_xref (
    card_number VARCHAR(16) NOT NULL,
    account_id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (card_number, account_id, customer_id)
);

    Migration Notes: - CARD-NUM (PIC 9(16)) → card_number (VARCHAR(16)) - Add card_type for future expansion - Add issue_date for tracking - Preserve CARDXREF structure

    Transaction Schema (transaction_db)

    Source: TRANSACT VSAM file (CVTRA05Y copybook)

    CREATE TABLE transactions (
    transaction_id VARCHAR(16) PRIMARY KEY,
    transaction_type VARCHAR(2) NOT NULL,
    category_code VARCHAR(4),
    source VARCHAR(10),
    description VARCHAR(100),
    amount DECIMAL(11,2) NOT NULL,
    card_number VARCHAR(16) NOT NULL,
    merchant_id VARCHAR(9),
    merchant_name VARCHAR(50),
    merchant_city VARCHAR(50),
    merchant_zip VARCHAR(10),
    original_timestamp TIMESTAMP NOT NULL,
    processed_timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status VARCHAR(20) DEFAULT 'POSTED', -- PENDING, POSTED, REVERSED
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    version INTEGER DEFAULT 0
);

CREATE INDEX idx_transactions_card ON transactions(card_number, original_timestamp DESC);
CREATE INDEX idx_transactions_date ON transactions(original_timestamp);
CREATE INDEX idx_transactions_type ON transactions(transaction_type);
CREATE INDEX idx_transactions_status ON transactions(status);

-- Transaction types reference
CREATE TABLE transaction_types (
    type_code VARCHAR(2) PRIMARY KEY,
    type_name VARCHAR(50) NOT NULL,
    description VARCHAR(100),
    debit_credit_indicator CHAR(1) NOT NULL, -- D=Debit, C=Credit
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Transaction categories reference
CREATE TABLE transaction_categories (
    category_code VARCHAR(4) PRIMARY KEY,
    category_name VARCHAR(50) NOT NULL,
    description VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

    Data Migration Approach

    Phase 1: Schema Creation

    1. Create PostgreSQL databases for each service
    2. Run DDL scripts to create tables, indexes, constraints
    3. Create database users and grant permissions
    4. Set up connection pools and monitoring

    Phase 2: Historical Data Migration

    Approach: One-time bulk migration of historical data

    Tools: - Custom Java migration utility - Spring Batch for large-volume processing - JDBC for database connectivity - CSV as intermediate format

    Process: 1. Extract from VSAM files: - Use COBOL programs or file utilities to export VSAM to CSV - One CSV file per VSAM file - Include all records with proper field delimiters

    1. Transform data:
    2. Convert data types (COMP-3 to decimal, dates to ISO format)
    3. Handle null values and defaults
    4. Validate data integrity
    5. Generate surrogate keys if needed

    6. Split data across microservice databases

    7. Load into PostgreSQL:

    8. Use COPY command for bulk loading
    9. Disable indexes during load, rebuild after
    10. Load in dependency order (customers → accounts → cards → transactions)
    11. Validate record counts and data integrity

    @Component
public class VsamToPostgresMigrator {

                    "last_name, address_line1, ...) " +
                    "FROM '" + csvFilePath + "' " +
                    "DELIMITER ',' CSV HEADER";
        jdbcTemplate.execute(sql);
    }

    public void migrateAccounts(String csvFilePath) {
        // Similar COPY command for accounts
    }

}

    Phase 3: Incremental Data Sync

    Approach: Keep mainframe and PostgreSQL in sync during transition

    Options:

    Option A: Dual Write Pattern - Application writes to both VSAM and PostgreSQL - Read from PostgreSQL, fallback to VSAM - Requires modification of COBOL programs

    Option B: Change Data Capture (CDC) - Capture changes from VSAM files - Replicate to PostgreSQL in near real-time - Tools: IBM InfoSphere CDC, custom batch jobs

    Option C: Event-Based Sync - Publish events for all data changes - Event consumers update PostgreSQL - Kafka or MQ as event bus

    Recommended: Option C (Event-Based Sync) - Least intrusive to mainframe - Enables gradual migration - Provides audit trail

    Phase 4: Data Validation

    Validation Checks: 1. Record count comparison (VSAM vs PostgreSQL) 2. Sample data verification (random records) 3. Referential integrity checks 4. Business rule validation 5. Performance testing

    Validation Script:

    -- Count validation
SELECT 'CUSTOMERS' as table_name, COUNT(*) as pg_count FROM customers;
-- Compare with VSAM record count

-- Sample data validation
SELECT * FROM customers WHERE customer_id = 1;
-- Compare with VSAM record

-- Referential integrity
SELECT COUNT(*) FROM accounts a 
LEFT JOIN customers c ON a.customer_id = c.customer_id 
WHERE c.customer_id IS NULL;
-- Should return 0

    Data Synchronization Strategy

    During Migration Period: 1. Mainframe remains system of record 2. PostgreSQL is read replica 3. Sync frequency: Real-time (events) or batch (hourly/daily) 4. Conflict resolution: Mainframe wins

    After Cutover: 1. PostgreSQL becomes system of record 2. Mainframe decommissioned or archived 3. No more synchronization needed
